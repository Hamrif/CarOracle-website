Project Overview

Vision Statement

CarOracle is a vehicle recommendation tool designed to make car buying easier for everyday consumers. Many people know what they want from a car, such as staying within a budget, saving money on fuel, having enough space for passengers, or finding a reliable vehicle for daily commuting. However, they often struggle to compare vehicles because traditional automotive websites and dealerships focus heavily on technical specifications and industry terminology that can be difficult to understand.

Our goal is to bridge the gap between real-world needs and vehicle data. Instead of requiring users to evaluate complex details such as horsepower, engine configurations, or cargo measurements, CarOracle allows them to focus on what matters most to their lifestyle. Through a simple and intuitive interface, users can indicate their priorities and preferences, and the application analyzes available vehicle options to provide personalized recommendations.

CarOracle is built for students, first-time buyers, commuters, and anyone who wants a practical and reliable vehicle without spending hours researching automotive specifications. We believe that buying a car should be a straightforward and informed experience rather than an overwhelming one.

Our vision is to empower consumers to make confident purchasing decisions based on their actual needs. By simplifying the vehicle selection process and presenting clear, data-driven recommendations, CarOracle helps users avoid unnecessary costs, reduce uncertainty, and find vehicles that truly fit their lifestyle. We aim to transform car buying from a confusing and stressful process into one that is simple, transparent, and user-focused.

Furthermore, the system must objectively reduce catalog overwhelm and save user’s time. The application is successful when it processes a pre-loaded catalog of vehicles and accurately narrows it to shortlist using user-defined lifestyle parameters. To prove it eliminates decision fatigue, users must be able to input their slider preferences, generate a matched list, and launch a head-to-head comparison.

Finally, we measure success by how reliably the app listens to the user's limits. The app is successful when 100% of the recommended cars respect the user's limits. For example, the app must never show a car that goes over the user's declared maximum budget. This strict filtering guarantees that buyers are only looking at practical options that fit their wallet and their daily life.

Development Reflection

What Changed, What We Learned

An honest account of the technical decisions we made, the architectural problems we hit, and how the system evolved across three iterations.

Major Issue · Iteration 2

Dealbreaker Constraints Bloated UI State

In Iteration 2, we introduced "dealbreaker" constraints—hard limits to completely exclude a vehicle. On paper, it was a useful power feature. In practice, managing the state between continuous slider values and binary dealbreaker toggles led to unpredictable behavior. Our JavaFX controllers became bloated trying to reconcile the conflicting logic. Worse, the results page became ambiguous: users could not tell if a car was missing because it was a poor slider match or because a dealbreaker silently removed it.

Response · Iteration 3

Refactoring to a Slider-Only Preference Model

Following user feedback, we removed dealbreakers entirely. The filter system was refactored to rely solely on the weighted preference sliders, producing a predictable list. Instead of deciding if any constraint was firm based on the dealbreakers, all search parameters were always considered when filtering cars. This simplification drastically cleaned up our JavaFX controller logic, made the interface trustworthy, and made the underlying domain code significantly easier to test.

What Worked Well

Clean Architecture & Design Patterns

Striving for separation of concerns provided a strong foundation, especially within our business layer. While maintaining strict boundaries across every service was a learning curve, utilizing the Builder pattern for vehicle creation and keeping the presentation layer thin successfully protected our core domain logic. This approach allowed tests to run seamlessly against in-memory stubs, enabling our transition to SQLite without altering business rules.

What Worked Well

Iterative GitLab Workflow

Using GitLab properly—with disciplined branching and merge request reviews—prevented merge conflicts from halting progress. It allowed teammates working on the persistence layer to push database schema changes without breaking the ongoing UI controller development happening on other branches.

What Didn't Work

Feature Complexity Without Validation

Building the dealbreaker logic taught us a hard lesson about over-engineering. We built a complex backend feature before validating if our target demographic (students and everyday commuters) actually wanted it. It conflicted with simpler, more vital functionality.

Architectural Decision

Applying SOLID Principles

To keep the codebase maintainable, we strictly adhered to SOLID principles, particularly the Single Responsibility Principle. Our JavaFX controllers only handle view updates and user inputs, immediately passing data off to dedicated service classes. This made tracking down UI bugs incredibly fast.

Technical Debt

Remaining Limitations

Currently, the application loads the entire vehicle database into the catalogue at startup rather than retrieving data in smaller, paginated chunks as needed. While this approach may initially simplify data access, it introduces several performance and scalability concerns. In particular, loading the full dataset at once creates a significant spike in memory usage, which can negatively impact overall system performance and may slow down the user’s device, especially as the dataset continues to grow over time.

In addition, the catalogue is refreshed every time the user exits the favourites screen in order to reflect any changes to a vehicle’s favourited status. Although this ensures data consistency, it further contributes to unnecessary reloading and processing of the entire dataset, even when only a small subset of records may have changed. As the number of vehicles increases, the time required to rebuild and render the catalogue also increases proportionally, leading to a less responsive user experience.

Another limitation is that the vehicle catalogue is currently seeded from a static CSV file at application startup. This means that new vehicles cannot be added dynamically during runtime, and any updates require modifications to the source file and a restart or redeployment of the application. As a result, the system lacks flexibility and does not support administrative management of vehicle data through a dedicated interface.

Finally, input validation issues within the service layer are currently handled by throwing exceptions, which are not always translated into meaningful or user-friendly error messages in the UI. This can lead to confusing or abrupt user experiences when invalid input is encountered, rather than providing clear feedback that guides the user toward correcting their input.

If Starting Over

Test-Driven UI Development

If we were starting the project again from scratch, one of the biggest things we would do differently is apply the SOLID principles more consistently throughout the entire application. We did a good job keeping our business layer separated and organized, but the presentation layer gradually became responsible for too many different tasks. As the project grew and more features were added, the UI became increasingly tied to application logic and persistence, making changes and refactoring more difficult than expected.

Looking back, we would establish clearer responsibilities for UI classes from the beginning, use dependency injection more consistently, and be more careful about avoiding duplicated logic. These changes would make the codebase easier to test, maintain, and extend as new requirements emerge.

We would also place a stronger emphasis on keeping the project structure organized from day one. Over time, even small inconsistencies in file organization can make it harder to navigate the codebase and collaborate effectively as a team. Maintaining a clean and well-structured repository would improve development efficiency and make implementing new features much smoother.
